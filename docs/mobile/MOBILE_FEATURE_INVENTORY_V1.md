# MOBILE FEATURE INVENTORY V1

**Тип документа:** классификация функций платформы по пригодности для
мобильного приложения.
**Дата:** 2026-08-01
**Коммит:** `f681584`
**Основание:** `MOBILE_PLATFORM_DISCOVERY_V1.md`,
`MOBILE_API_CAPABILITY_MATRIX_V1.md`

Классификация опирается **только на состояние репозитория**. Там, где
отнесение функции к категории зависит от решения человека, функция помещена
в раздел «Требует продуктового решения», а не отнесена произвольно.

Каждая функция принадлежит **одной основной категории**. Функции из
категорий «Требует backend-изменений» и «Требует продуктового решения»
дополнительно помечены целевой категорией — куда они попадут после снятия
ограничения.

## 1. MVP

Функции, которые (а) существуют в вебе, (б) образуют минимальный связный
путь клиента и (в) технически достижимы. Помечены готовностью из матрицы.

### 1.1 MVP — работает без изменений backend

| # | Функция | Готовность | Механизм |
|---|---|---|---|
| M-01 | Вход по email и паролю | 🟢 | Мобильный Supabase SDK `signInWithPassword` |
| M-02 | Выход | 🟢 | SDK `signOut` |
| M-03 | Просмотр статуса своего кейса | 🟢 | SDK select, RLS `client_cases_select_own` |
| M-04 | Просмотр истории кейса | 🟢 | SDK select, RLS `case_lifecycle_events_select_own` |
| M-05 | Список своих документов | 🟢 | SDK select, RLS `uploaded_documents_select_own` |
| M-06 | Открытие своего документа (signed URL 60 с) | 🟢 | SDK `createSignedUrl` |
| M-07 | Загрузка файла в Storage | 🟢 | SDK Storage `upload`, path-based RLS |
| M-08 | Список своих оплат | 🟢 | SDK select, RLS `payments_select_own` |
| M-09 | Состояние периода сопровождения | 🟢 | SDK select, RLS `service_periods_select_own` |
| M-10 | История своих обращений в поддержку | 🟢 | SDK select, RLS `support_requests_select_own` |
| M-11 | Счётчик непрочитанных от команды | 🟢 | SDK count по `case_messages` |
| M-12 | Баланс и история токенов | 🟢 | SDK select, RLS `token_transactions_select_own` |
| M-13 | Реферальный код и список приглашённых | 🟢 | SDK select, RLS `referrals_select_own` |
| M-14 | Экран «сейчас важно» (следующий шаг) | 🟢 | Вычисляется на клиенте из M-03 и M-05 |
| M-15 | Экстренное уведомление (кризисный блок) | 🟢 | Статический контент — **обязателен** |
| M-16 | Просмотр публичной оферты (PDF) | 🟢 | Прямой URL + нативный просмотрщик |

**16 функций MVP не требуют ни одного изменения на backend.** Этого
достаточно для полноценного read-only мобильного кабинета: человек видит
свой кейс, документы, оплаты, переписку и токены.

## 2. Post-MVP

Функции, существующие в вебе, но не входящие в минимальный путь клиента.

| # | Функция | Основание для отнесения |

| P-09 | Копирование реферального кода | Тривиально, но не критично |
| P-10 | Погашение токенов в промокод | Требует нового эндпоинта (Stripe secret API); ценность появляется только вместе с решением по оплате (MB-06) |

## 5. Prohibited for mobile

Категорический запрет. Нарушение любого пункта создаёт риск, несоизмеримый
с выигрышем. Подробные правила — в `MOBILE_SECURITY_BOUNDARY_V1.md`.

| # | Запрещено | Основание |
|---|---|---|
| PR-01 | Помещать `SUPABASE_SERVICE_ROLE_KEY` в приложение любым способом | Ключ полностью обходит RLS всех 19 таблиц (`lib/supabase/service.ts:27-32`). Мобильный бандл извлекается тривиально |
| PR-02 | Помещать `STRIPE_SECRET_KEY` или `STRIPE_WEBHOOK_SECRET` в приложение | Доступ к платёжному аккаунту |
| PR-03 | Помещать `ANTHROPIC_API_KEY` или `OPENAI_API_KEY` в приложение | Прямой финансовый ущерб при утечке |
| PR-04 | Помещать `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` в приложение | Доступ к каналу внутренних оповещений команды |
| PR-05 | Помещать `ASSISTANT_USAGE_SALT` в приложение | Соль для хэширования IP-адресов посетителей |
| PR-06 | Вызывать Stripe API напрямую из приложения | Следствие PR-02 |
| PR-07 | Вызывать Anthropic/OpenAI API напрямую из приложения | Обходит guardrails (`lib/assistant/guard.ts`), тиры, красные флаги и системные промпты |
| PR-08 | Обходить `/api/assistant/client` для получения ответов ИИ | Отключает авто-эскалацию красных флагов — механизм безопасности человека |
| PR-09 | Дублировать в приложении логику интерпретации медицинских данных | Конституция центра: решения по кейсу принимает Карен, не ИИ и не приложение |
| PR-10 | Записывать `client_cases` / `onboarding_submissions` напрямую через SDK | Создаст кейс без согласий и без аудита (см. M-23) |
| PR-11 | Записывать `consent_records` напрямую через SDK | Согласия должны фиксироваться серверной логикой с корректной версией оферты |
| PR-12 | Пытаться читать `admin_notes` | Политика `using (false)` — закрыто на уровне БД (миграция строка 584) |
| PR-13 | Пытаться читать `assistant_knowledge`, `notification_events`, `stripe_events`, `assistant_usage` | RLS включён, клиентских политик нет — доступ только service-role |
| PR-14 | Изменять `profiles.role` или `profiles.status` | Триггер перезаписывает эти поля, но попытка сама по себе — сигнал компрометации |
| PR-15 | Изменять статус, владельца, кейс или путь своего документа | Триггер `prevent_uploaded_document_client_tampering` бросает исключение |
| PR-16 | Читать документы других пользователей через Storage | Storage RLS требует `auth.uid()` первым сегментом пути |
| PR-17 | Показывать пользователю сырые сообщения об ошибках Postgres | Раскрытие внутренностей БД (SR-10) |
| PR-18 | Логировать содержимое медицинских документов, сообщений чата или диалогов ИИ | Даже платформа усечает фрагменты до 600 символов при отправке команде |
| PR-19 | Интерпретировать маркер `[RED_FLAG:...]` на клиенте | Маркер вырезается сервером; клиент его не видит и не должен реконструировать |
| PR-20 | Отключать или ослаблять RLS ради удобства мобильного клиента | `README.md:129-130`: «Do not weaken RLS» |

**Главный вывод инвентаризации:** полноценный read-only мобильный кабинет
(16 функций) достижим **без единого изменения backend**. Каждое следующее
приращение имеет чёткую цену: BC-01 открывает 5 функций, пять новых
эндпоинтов (BC-06 … BC-09, BC-13) закрывают весь путь клиента от регистрации
до переписки, push (BC-16) — единственная действительно новая
инфраструктура.
