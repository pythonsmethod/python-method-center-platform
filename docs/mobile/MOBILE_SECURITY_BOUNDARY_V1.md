# MOBILE SECURITY BOUNDARY V1

**Тип документа:** граница безопасности мобильного приложения Pythons Method
Center.
**Дата:** 2026-08-01
**Коммит:** `f681584`
**Основание:** `MOBILE_PLATFORM_DISCOVERY_V1.md`

## Статус документа

Это **обязательные границы**, а не рекомендации. Они выведены из того, что
платформа уже делает: каждое правило ниже либо повторяет существующую
защиту веб-платформы, либо закрывает риск, который появляется именно из-за
мобильного клиента.

Правило простое: **мобильное приложение не может быть менее защищённым, чем
веб.** Оно работает с медицинскими материалами людей в тяжёлых жизненных
обстоятельствах, живёт на устройстве, которое можно потерять, и
распространяется в виде бандла, который можно распаковать.

Изменение любого правила требует явного решения владельца платформы,
зафиксированного в новой версии этого документа.

## 1. Какие данные мобильное приложение может получать

Разрешение основано на реальных RLS-политиках базы. Приложение получает
данные **под собственной сессией пользователя** — никогда под service-role.

### 1.1 Разрешено получать

| Данные | Таблица / источник | Основание (RLS) |
|---|---|---|
| Свой профиль: email, имя, телефон, локаль, роль, статус | `profiles` | `profiles_select_own` (миграция строка 465) |
| Свой кейс: номер, статус, срочность, направление, цель, описание, даты | `client_cases` | `client_cases_select_own` (строка 481) |
| Свою анкету | `onboarding_submissions` | `onboarding_submissions_select_own` (строка 491) |
| Метаданные своих документов | `uploaded_documents` | `uploaded_documents_select_own` (строка 507) |
| Свои оплаты: продукт, статус, сумма, валюта, даты | `payments` | `payments_select_own` (строка 523) |
| Свои периоды сопровождения | `service_periods` | `service_periods_select_own` (строка 533) |
| Историю своего кейса | `case_lifecycle_events` | `case_lifecycle_events_select_own` (строка 538) |
| Свои обращения в поддержку | `support_requests` | `support_requests_select_own` (строка 543) |
| Свои эскалации (красные флаги) | `escalation_events` | `escalation_events_select_own` (строка 559) |
| Свой аудит-лог | `audit_logs` | `audit_logs_select_own` (строка 569) |
| Свои согласия | `consent_records` | `consent_records_select_own` (строка 574) |
| Свою переписку по кейсу | `case_messages` | `case_messages_select_own` (`20260722150000:32`) |
| Своих приглашённых | `referrals` | `referrals_select_own` (`20260725120000:45`) |
| Свой ledger токенов | `token_transactions` | `token_transactions_select_own` (`20260725140000:36`) |
| Свои файлы в Storage по временной ссылке | bucket `client-documents` | Storage RLS: первый сегмент пути = `auth.uid()` |
| Свои голосовые сообщения по временной ссылке | bucket `case-audio` | через `/api/messages/thread` |
| Ответы ИИ-помощника | `POST /api/assistant/client` | — |
| Публичный контент: оферта, лендинг, тарифы | публичные страницы | — |

### 1.2 Запрещено получать

| Данные | Основание запрета |
|---|---|
| Внутренние заметки команды (`admin_notes`) | Политика `using (false)` — закрыто на уровне БД (строка 584) |
| База знаний ИИ (`assistant_knowledge`) | RLS включён, клиентских политик нет |
| Журнал уведомлений (`notification_events`) | Только service-role |
| События Stripe (`stripe_events`) | Только service-role |
| Счётчики ИИ (`assistant_usage`) | Только service-role, права отозваны у `authenticated` явно (`20260728120000:65-67`) |
| Любые данные другого пользователя | RLS + Storage path RLS |
| Полный список кейсов, документов, оплат платформы | Доступно только через service-role |
| Системные промпты ИИ | Формируются на сервере, наружу не отдаются |
| Скрытый маркер `[RED_FLAG:...]` | Вырезается сервером до отправки клиенту (`lib/assistant/red-flags.ts:18-25`) |

### 1.3 Правило минимальной достаточности

Приложение запрашивает **только те поля, которые показывает на экране**.
`select("*")` запрещён: он тянет на устройство данные, которые не нужны и
которые придётся защищать. Веб-платформа уже следует этому правилу — везде
перечисляются конкретные столбцы (`lib/cases/queries.ts:41-43`,
`lib/messages/queries.ts:111-113`).

## 2. Какие данные приложение НЕ должно хранить локально

Разделение по классам. Класс определяет, что можно положить на диск.

### 2.1 Запрещено к постоянному хранению — категорически

| Данные | Почему |
|---|---|
| Файлы медицинских документов (PDF, снимки, анализы) | Самые чувствительные данные платформы. Утеря устройства = утечка |
| Аудиофайлы голосовых сообщений | Содержат ту же информацию, что и документы |
| Signed URL любого файла | В вебе живут 60 секунд для документов и 1 час для аудио. Хранение на диске отменяет весь смысл ограниченного срока |
| Полный текст переписки с командой | Медицинский контекст |
| Полные тексты диалогов с ИИ | Платформа их сама не хранит (`README.md:70`) — приложение не должно быть менее строгим |
| Содержимое анкеты (`onboarding_submissions.payload`) | Описание ситуации человека и того, о ком он заботится |
| Данные о состоянии здоровья в любом виде | — |
| Пароль пользователя | Ни в каком виде, включая «запомнить для автозаполнения» |
| Любой серверный секрет | См. раздел 9 |

### 2.2 Допустимо хранить в памяти только на время сессии

- Метаданные документов (имя файла, размер, статус, дата)
- Статус кейса, направление, срочность
- Лента сообщений текущего экрана
- Баланс токенов, реферальный код
- Список оплат

Эти данные очищаются при выходе, при переходе приложения в фон дольше
установленного порога и при отзыве сессии.

### 2.3 Допустимо хранить постоянно

- Токены сессии — **исключительно** в защищённом хранилище ОС (раздел 3)
- Настройки интерфейса: язык, тема, флаг «приветствие ИИ показано»
- Идентификатор устройства для push (когда push появится — BC-16)
- Флаг прохождения онбординга приложения

### 2.4 Временные файлы

- Файл, выбранный для загрузки, живёт в временной директории **только до
  завершения загрузки** и удаляется сразу после — независимо от того,
  успешной была загрузка или нет.
- Записанное голосовое сообщение удаляется сразу после успешной отправки.
  При неуспешной отправке — удаляется при выходе из экрана чата.
- Скачанный для просмотра документ удаляется при закрытии просмотрщика.
- Кэш изображений системных компонентов **отключается** для любого контента
  из `client-documents` и `case-audio`.
- При выходе из аккаунта временная директория приложения очищается
  полностью.

Веб-платформа демонстрирует этот принцип: вложения ИИ команды «не хранятся
нигде — файл едет с одним запросом к модели и исчезает»
(`lib/assistant/attachments.ts:3-6`); при провале записи метаданных
загруженный объект удаляется из Storage
(`app/(client)/cabinet/DocumentUploadPanel.tsx:183-185`,
`app/api/messages/audio/route.ts:151`).

### 2.5 Скриншоты и превью задач

Экраны с документами, перепиской и анкетой должны быть исключены из
системных снимков переключателя задач. Это относится к iOS и Android
одинаково.

## 3. Правила хранения токенов

### 3.1 Где

| Платформа | Единственно допустимое хранилище |
|---|---|
| iOS | Keychain, с атрибутом доступности не выше `WhenUnlockedThisDeviceOnly` |
| Android | EncryptedSharedPreferences / Keystore |

### 3.2 Где запрещено

- `UserDefaults` / `SharedPreferences` без шифрования
- Обычные файлы, SQLite, Realm, любое хранилище приложения
- Логи любого уровня
- Резервные копии устройства и облачная синхронизация (iCloud Keychain
  синхронизация для токенов сессии — **отключена**)
- Аналитика, крэш-репорты, отчёты об ошибках
- Передача токена в любой сторонний SDK
- Запись токена в URL, query-параметры или заголовки сторонних сервисов

### 3.3 Жизненный цикл

- Access-token обновляется штатным механизмом Supabase SDK — вручную
  refresh-токен не обрабатывается. Веб делает то же самое (`middleware.ts:74`).
- Refresh-токен **никогда не покидает** защищённое хранилище.
- При выходе оба токена удаляются, и вызывается серверный `signOut`.
- При получении 401 от любого эндпоинта приложение очищает сессию и ведёт
  пользователя на экран входа — молчаливый повтор запроса запрещён.
- Если приложение обнаруживает признаки компрометации устройства (jailbreak
  / root), запись токенов в постоянное хранилище **не выполняется**; сессия
  живёт только в памяти.

### 3.4 Что запрещено делать с cookie

Обходить MB-01 через ручную подстановку cookie `sb-*` в HTTP-запросы
**запрещено**. Это уводит сессию из защищённого хранилища ОС в сетевой слой
приложения и создаёт риск SR-04. Если Bearer-аутентификация ещё не
реализована на backend, соответствующие функции остаются недоступными в
приложении — это допустимое ограничение, в отличие от небезопасного обхода.

## 4. Правила логирования

### 4.1 Никогда не логируется

| Категория | Примеры |
|---|---|
| Токены и секреты | access, refresh, любые ключи |
| Учётные данные | email в паре с паролем, сам пароль |
| Медицинский контент | содержимое документов, имена файлов документов, тексты сообщений, тексты диалогов ИИ, содержимое анкеты |
| Персональные данные | ФИО, телефон, адрес |
| Signed URL | они сами по себе дают доступ к файлу |
| Сырые ответы Postgres | раскрывают структуру БД (SR-10) |
| Тела запросов и ответов клиентских эндпоинтов | могут содержать всё перечисленное выше |

### 4.2 Допустимо логировать

- Идентификаторы событий и корреляционные ID
- HTTP-статусы и коды ошибок (не тексты)
- Длительность операций, метрики производительности
- Навигация по экранам без параметров
- Факт «документ загружен» **без** имени файла и без размера

### 4.3 Эталон платформы

Веб-платформа усечёт даже то, что отправляет своей же команде:

- Фрагмент сообщения при красном флаге обрезается до 600 символов
  (`lib/assistant/red-flags.ts:69`) и дополнительно усечён при отправке
  (`truncateExcerpt`, строка 109).
- Уведомление о новом сообщении клиента **не содержит текста сообщения** —
  только «Откройте чат кейса, чтобы прочитать и ответить»
  (`lib/messages/actions.ts:71-77`).
- IP-адреса не хранятся в сыром виде — только SHA-256 с солью
  (`lib/assistant/guard.ts:60-64`).

Мобильное приложение соблюдает **не менее строгий** стандарт.

### 4.4 Крэш-репорты и аналитика

- Крэш-репортер, если он используется, настраивается с явным списком
  разрешённых полей, а не с фильтрацией запрещённых.
- Автоматический сбор содержимого экранов, значений полей ввода и
  сетевых запросов **отключается**.
- Стек-трейсы очищаются от значений переменных.
- Аналитика не получает ни одного поля из раздела 4.1.

### 4.5 Показ ошибок пользователю

Пользователю показывается человеческое сообщение, а не техническое.
Сообщения об ошибках Postgres, приходящие с сервера (`errorState(error.message)`
в `lib/documents/actions.ts:88` и аналогичных местах), **не отображаются
как есть** — приложение сопоставляет их с собственным словарём сообщений.

## 5. Правила работы с документами

### 5.1 Загрузка

- Путь строится **строго** как `{userId}/{caseId}/{documentId}/{safeFilename}`
  (`lib/documents/config.ts:117-129`). Storage RLS отклонит любой другой.
- Имя файла санитизируется **той же логикой**, что в
  `sanitizeOriginalFilename` (`lib/documents/config.ts:43-56`): последний
  сегмент пути, удаление управляющих символов, приведение к ASCII, максимум
  160 символов. Расхождение приведёт к отклонению регистрации метаданных
  серверной проверкой (`lib/documents/actions.ts:76-78`).
- Валидация до отправки: размер ≤ 25 МБ, MIME из списка `application/pdf`,
  `image/png`, `image/jpeg`, `image/webp` (`lib/documents/config.ts:3-10`).
- `upsert: false` — перезапись существующего объекта запрещена.
- При провале регистрации метаданных загруженный объект **удаляется**, как
  это делает веб (`DocumentUploadPanel.tsx:183-185`).

### 5.2 Просмотр

- Только через `createSignedUrl(path, 60)` под сессией пользователя.
- Signed URL используется **немедленно** и не сохраняется: ни в состоянии
  приложения дольше времени просмотра, ни на диске, ни в логах, ни в истории
  навигации.
- Просмотр — во встроенном просмотрщике приложения. Передача signed URL во
  внешний браузер или стороннее приложение запрещена: URL попадёт в историю
  и в буфер другого процесса.
- Кэширование содержимого просмотрщиком отключается.
- По истечении 60 секунд URL перезапрашивается, а не переиспользуется.

### 5.3 Голосовые сообщения

- Отправка — только через `POST /api/messages/audio`, multipart.
- Ограничения: ≤ 10 МБ, длительность 0–3600 секунд, MIME из `audio/webm`,
  `audio/mp4`, `audio/mpeg`, `audio/ogg`, `audio/wav`
  (`app/api/messages/audio/route.ts:11-19`).
- `audioUrl` в ленте чата подписан на **1 час** (`lib/messages/queries.ts:4`).
  Приложение не кэширует ни URL, ни скачанный файл дольше текущего сеанса
  просмотра экрана.
- Запись голоса требует явного разрешения на микрофон, запрашиваемого в
  момент первой записи, а не при старте приложения.

### 5.4 Права доступа устройства

Разрешения запрашиваются точечно и в момент использования:

| Разрешение | Когда | Зачем |
|---|---|---|
| Камера | При выборе «сфотографировать документ» | Загрузка документа |
| Галерея / файлы | При выборе файла | Загрузка документа |
| Микрофон | При первой записи голосового | Голосовое сообщение |
| Уведомления | Когда push будет реализован (BC-16) | Сообщения от команды |

Разрешения на геолокацию, контакты, календарь, здоровье (HealthKit / Google
Fit) **не запрашиваются** — платформа таких данных не собирает.

## 6. Правила удаления временных файлов

| Событие | Что удаляется |
|---|---|
| Успешная загрузка документа | Временная копия выбранного файла |
| Неуспешная загрузка документа | Временная копия + объект в Storage, если он успел загрузиться |
| Успешная отправка голосового | Локальная запись |
| Выход с экрана чата | Неотправленные записи голоса |
| Закрытие просмотрщика документа | Скачанная копия и signed URL |
| Переход приложения в фон | Данные экранов с медицинским содержимым — из памяти |
| Выход из аккаунта | **Вся** временная директория, весь кэш изображений, все данные разделов 2.1 и 2.2, токены |
| Отзыв сессии сервером (401) | То же, что при выходе |
| Обнаружение jailbreak / root | То же, что при выходе; постоянное хранение токенов не выполняется |

Удаление выполняется явно, а не полагается на политику очистки кэша ОС.
Отложенное удаление — недопустимо: между «пометили» и «удалили» устройство
может быть изъято или потеряно.

## 7. Роли и доступ

### 7.1 Клиентское приложение

- Работает **только** с ролью `client`.
- Роль читается из `profiles.role`, но является **отображаемой, а не
  разрешающей**: фактический доступ определяет RLS на стороне БД. Приложение
  никогда не принимает решение о доступе к данным на основе роли,
  прочитанной локально.
- Если у вошедшего профиля роль `support`, `admin` или `karen`, клиентское
  приложение работает с ним **как с клиентом** — административные функции
  не появляются. Мобильная админка — отдельный продукт (см. 7.3).
- Профиль со статусом `suspended` или `closed` не допускается к работе:
  веб-платформа отказывает таким профилям в доступе даже к `/admin`
  (`lib/auth/require-staff.ts:65-72`), клиентское приложение обязано вести
  себя так же.

### 7.2 Что приложение никогда не делает с ролями

- Не пытается изменить `profiles.role` или `profiles.status`. Триггер
  `protect_profile_staff_fields_from_client` перезапишет эти поля
  (`20260623040000:12-28`), но сама попытка — признак компрометации клиента.
- Не реализует локальную проверку «является ли пользователь персоналом» как
  единственный gate доступа к данным.
- Не хранит и не кэширует решения об авторизации между сессиями.

### 7.3 Приложение для команды

Мобильное приложение для персонала — **отдельный продукт с отдельной
границей безопасности**, который эта версия документа не покрывает.
Основание: административный доступ реализован через service-role
(`lib/cases/staff-actions.ts`, `lib/support/actions.ts:151`), а
service-role в мобильном приложении запрещён абсолютно (раздел 9).
Мобильная админка потребовала бы полностью нового серверного API и
собственного документа границ.

## 8. Risk and escalation boundary

Приложение работает с людьми в тяжёлых ситуациях. Ошибка на этой границе
стоит дороже любой технической.

### 8.1 Красные флаги — что приложение делает и чего не делает

**Делает:**
- Передаёт сообщения пользователя в `POST /api/assistant/client` без
  изменений. Серверный конвейер эскалации срабатывает автоматически
  (`lib/assistant/red-flags.ts:32-116`).
- Показывает ответ ИИ ровно так, как он пришёл с сервера.
- Всегда держит доступным блок экстренной помощи (`components/EmergencyNotice.tsx`).

**Не делает:**
- Не пытается самостоятельно определять кризисную ситуацию.
- Не реконструирует и не интерпретирует маркер `[RED_FLAG:...]` — сервер
  вырезает его до отправки, и приложение не должно знать о его
  существовании.
- Не фильтрует, не сокращает и не переписывает ответы ИИ.
- Не подавляет и не откладывает отображение ответа, содержащего указание на
  экстренную помощь.
- Не блокирует отправку сообщения из-за его содержания.

### 8.2 Целостность канала эскалации

Обход `/api/assistant/client` — прямое обращение к Anthropic или OpenAI из
приложения — **отключает механизм спасения человека**. Это не вопрос
экономии токенов: без серверного конвейера красный флаг не будет записан в
`escalation_events` и команда не получит оповещение. Запрещено абсолютно
(PR-07, PR-08).

### 8.3 Деградация сети

- Если отправка сообщения не удалась, приложение сообщает об этом **явно и
  немедленно**. Молчаливая постановка в очередь для медицинского контекста
  недопустима: человек будет считать, что его услышали.
- Экстренный блок с контактами доступен **офлайн** — он статичен и должен
  быть встроен в приложение, а не загружаться с сервера.
- Приложение никогда не показывает устаревшие данные кейса без явной
  пометки «данные могли устареть».

### 8.4 Что приложение не решает

- Не интерпретирует медицинские данные.
- Не оценивает срочность кейса. Срочность (`case_urgency`) — durable-поле,
  которым владеет Карен; комментарий в схеме фиксирует это прямо: «Karen
  owns durable case decisions; AI/System do not set official urgency or
  status» (миграция строка 206-207).
- Не даёт рекомендаций от своего имени.
- Не изменяет статус кейса.

## 9. Запрет на хранение серверных секретов в приложении

### 9.1 Абсолютный запрет

Ни одна из этих переменных не попадает в мобильное приложение — ни в код,
ни в ресурсы, ни в конфигурационные файлы, ни в CI-переменные сборки, ни в
удалённую конфигурацию:

| Переменная | Что даёт при утечке |
|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | **Полный обход RLS всех 19 таблиц.** Чтение и изменение данных всех клиентов платформы |
| `STRIPE_SECRET_KEY` | Доступ к платёжному аккаунту: создание купонов, возвраты, чтение платежей |
| `STRIPE_WEBHOOK_SECRET` | Подделка событий оплаты |
| `ANTHROPIC_API_KEY` | Прямой финансовый ущерб, использование от имени центра |
| `OPENAI_API_KEY` | То же |
| `TELEGRAM_BOT_TOKEN` | Доступ к каналу внутренних оповещений команды |
| `TELEGRAM_CHAT_ID` | Идентификация внутреннего канала |
| `ASSISTANT_USAGE_SALT` | Обращение хэшей IP-адресов посетителей |
| `FOUNDER_EMAILS` | Раскрытие allowlist кабинета основателя |
| `PAYMENT_ALT_*` | Банковские и криптореквизиты центра |

### 9.2 Почему запрет абсолютный

Мобильное приложение — это файл, который скачивает кто угодно. Распаковка
APK или IPA и извлечение строк — операция на несколько минут. «Обфускация»,
«разбиение строки на части», «шифрование с ключом внутри приложения» и
хранение в нативном коде не являются защитой: ключ расшифровки едет в том
же бандле.

Веб-платформа обеспечивает это на уровне кода:
`createSupabaseServiceClient()` бросает исключение при попытке вызова в
браузере — `assertServerRuntime()` проверяет `typeof window !== "undefined"`
(`lib/supabase/service.ts:6-10`). Мобильное приложение обязано соблюдать ту
же границу, хотя такой проверки в нём быть не может.

### 9.3 Что приложению разрешено содержать

| Значение | Основание |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` (аналог) | Публичен по дизайну |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` (аналог) | Публичен по дизайну; вся защита — на RLS |
| Базовый URL платформы | Публичен |

Anon-ключ безопасен **только потому**, что RLS корректно ограничен
`auth.uid()` на всех клиентских таблицах. Отсюда следует: **ослабление RLS
ради удобства мобильного клиента запрещено** (`README.md:129-130`).
Приложение не имеет права требовать расширения политик.

### 9.4 Требования к процессу

- Секреты не попадают в репозиторий мобильного приложения ни в каком виде.
- Сборочные CI-переменные, содержащие серверные секреты, не пробрасываются
  в мобильные конфигурации.
- Перед каждым релизом выполняется проверка бандла на наличие строк из
  раздела 9.1.
- При подозрении на утечку любого ключа он ротируется **немедленно**, до
  выяснения обстоятельств.

## 10. Границы ответственности ИИ

Раздел опирается на конституцию центра
(`docs/constitution/constitution_06_role_of_ai_extended.md`,
`constitution_08_boundaries_of_responsibility.md`) и на то, как ограничения
реализованы в коде.

### 10.1 Что ИИ делает в платформе сегодня

| Уровень | Кто | Что доступно ИИ |
|---|---|---|
| `guest` | Посетитель сайта | Только о центре, методе, регистрации, тарифах, первом шаге. Одна модель, короткие ответы, 15 сообщений в сутки |
| `registered` | Зарегистрирован | Плюс собственный статус кейса и следующий шаг. Одна модель, 60 сообщений в сутки |
| `client` | Оплатил | Плюс имена файлов документов, период сопровождения, история кейса. Две модели + арбитр, 200 сообщений в сутки |

Источник: `lib/assistant/tiers.ts:84-236`, `lib/assistant/guard.ts:32-58`,
`app/api/assistant/client/route.ts:20-29`.

### 10.2 Чего ИИ не делает — и что приложение не должно менять

- **Не читает содержимое медицинских документов.** В контекст попадают
  только имена файлов, и системный промпт фиксирует это дословно:
  «Содержимое файлов тебе НЕ доступно — только названия»
  (`lib/assistant/tiers.ts:203`). Ограничение подтверждено как известное в
  `README.md:68-69`.
- **Не ставит диагнозов, не назначает лечение, не обещает результат.** Это
  прямые критерии арбитра качества ответов
  (`lib/assistant/router.ts:77`).
- **Не устанавливает срочность и статус кейса.** Схема БД фиксирует это в
  комментарии к `escalation_events`: «These do not change durable case
  urgency or status; Karen owns those decisions» (миграция строка 329-330).
- **Не заменяет человека.** При исчерпании лимита ответ приглашает написать
  команде — «там отвечает живой человек» (`lib/assistant/guard.ts:71,74`).

### 10.3 Обязанности мобильного приложения

**Приложение обязано:**
- Передавать сообщения в ИИ только через `/api/assistant/client`.
- Отображать ответ без изменений.
- Ясно обозначать, что собеседник — ИИ-помощник, а не Карен и не команда.
- Сохранять визуальную границу между ИИ-чатом и чатом кейса с командой.
  В вебе это разные сущности: ИИ — виджет, команда — `case_messages`.
  Смешение их в одном интерфейсе создаст у человека ложное представление о
  том, кто ему отвечает.
- Показывать ответ об исчерпании дневного лимита как **обычное сообщение**,
  а не как ошибку. Сервер намеренно возвращает его со статусом 200
  (`app/api/assistant/client/route.ts:105-108`) — «человек должен прочитать
  тёплое приглашение, а не красный технический баннер».

**Приложению запрещено:**
- Реализовывать собственный ИИ, собственные промпты или собственную логику
  интерпретации.
- Кэшировать ответы ИИ и показывать их повторно как новые.
- Подставлять в историю диалога сообщения, которых пользователь не отправлял.
- Обходить лимиты через ретраи, ротацию идентификаторов или параллельные
  запросы.
- Скрывать от пользователя, что ответ дал ИИ.
- Использовать ИИ для триажа, приоритизации обращений или принятия решений
  о доступе.

### 10.4 История диалогов

Платформа **не сохраняет** историю диалогов с ИИ (`README.md:70`).
Следствия для приложения:

- Историю в пределах сессии приложение держит **в памяти** и присылает
  целиком с каждым запросом (сервер берёт последние `MAX_HISTORY_MESSAGES`).
- Постоянное хранение истории на устройстве **запрещено** (раздел 2.1) —
  иначе приложение станет хранилищем медицинских данных, которым платформа
  сознательно не является.
- Если продукт решит, что история нужна, это **решение о хранении
  медицинских данных**, требующее отдельного согласия пользователя,
  изменения политики приватности и новой версии этого документа (PD-12).
