# NEXORA MASTER ARCHITECTURE v1.0

Дата решения владельца: 23 сентября 2026.
Decision ID: NEXORA-2026-09-23-01.
Статус: APPROVED PRODUCT DIRECTION; RUNTIME MIGRATION NOT COMPLETE.

## 1. Решение владельца

NEXORA — общее интеллектуальное ядро экосистемы с переиспользуемыми возможностями.
Разбор документов — одна из возможностей NEXORA.

ANHAM — AI-система Python Method Center, которая использует возможности NEXORA
в контексте услуг, пользователей, ролей и методологии PMC.

Технологический продукт для внешних компаний и разработчиков — возможности
NEXORA через NEXORA API. ANHAM является прикладным потребителем этих возможностей,
а не владельцем отдельного универсального ядра.

ANKH выводится из целевой архитектуры как отдельное имя системы, ядра или продукта.
Его существующая полезная реализация становится основой возможности
«NEXORA — разбор документов». Исторические записи и технические идентификаторы
сохраняют происхождение до совместимого переноса; это не отдельная ветвь бизнеса.

## 2. Уровни и ответственность

| Уровень | Что ему принадлежит архитектурно | Что остаётся за его пределами |
|---|---|---|
| NEXORA Core | Общие контракты возможностей, маршрутизация моделей, управление контекстом и доступом, версии, выполнение и учёт операций | Специфичная методология PMC, его тарифы, роли и решения Карена |
| Возможности NEXORA | Разбор документов, извлечение фактов и источников, проверка качества, работа с разрешённой памятью, сравнение данных, диалог и голос через общие интерфейсы | Обещание, что все перечисленные возможности уже выделены и доступны через API |
| ANHAM / PMC application | Персона ANHAM, пользовательские сценарии PMC, настройка разрешённых возможностей, контекст конкретного Case, интерфейсы клиента и команды | Собственный дублирующий универсальный движок |
| PMC domain layer | Методология центра, предметные правила, человеческая проверка, решения Professor Python, услуги и доступ к ним | Автоматическое распространение этих правил на всех клиентов NEXORA |
| NEXORA API | Внешний доступ к принятым возможностям по версиям, правам, лимитам и договорённым условиям | Доступ к данным PMC или готовность к продаже до приёмки |

Целевая зависимость: приложения используют NEXORA. Общий код NEXORA не импортирует
персону ANHAM, названия тарифов PMC, роль Karen или конкретные patient/Case records.
Предметный адаптер PMC передаёт только разрешённые входы и получает типизированный результат.

Один технологический движок не означает одну общую память клиентов. Данные, история,
ключи, права и учёт использования ограничены организацией, приложением и разрешённым
субъектом. Личные знания владельца, данные PMC и данные внешнего заказчика не смешиваются.

## 4. Разбор документов NEXORA

Общая часть получает разрешённый документ и формирует проверяемый набор данных:
источник, извлечённые значения, единицы, даты, фрагменты происхождения,
неопределённость, противоречия и версии обработки.

Предметный модуль выбирает подходящие правила и типы документов. Для PMC это
медицинский контекст и существующая процедура проверки Кареном.

Пример целевого прохода PMC:

1. Клиент передаёт документ через ANHAM/кабинет PMC с существующими правами.
2. Адаптер PMC вызывает возможность NEXORA «разбор документов».
3. NEXORA возвращает структурированные данные, источники, качество и спорные места.
4. Предметные правила PMC готовят картину для Карена.
5. Карен проверяет и фиксирует решение в предусмотренном процессе.
6. ANHAM объясняет и показывает клиенту разрешённый результат.

SOURCE, EXTRACTED, VERIFIED, NORMALIZED, ANALYTICAL INTERPRETATION, KAREN DECISION
и CLIENT RESPONSE остаются различимыми слоями. Объединение под NEXORA не повышает
NEEDS_REVIEW до VERIFIED и не отменяет проверку источника.

Наличие медицинских парсеров не доказывает готовность разбора любых договоров,
финансовых файлов или других типов документов. Каждый новый предметный профиль
нуждается в собственной проверке.

## 5. ANHAM как AI-система Python Method Center

ANHAM сохраняет имя, характер, историю общения, пользовательскую ценность и
интерфейсы PMC. Возможности подключаются к NEXORA через адаптер с существующими
правами и предметными правилами.

Контекст и доступ определяются сервером. Связь с Case, представляемым пациентом,
решениями Карена и услугой принадлежит PMC. Новый общий аккаунт, второй Case или
копия медицинской истории ради этой архитектуры не создаются.

Продуктовый профиль: [ANHAM — PMC application architecture](ANHAM_PMC_APPLICATION_ARCHITECTURE.md).
Прежний master ANHAM становится подчинённым профилем приложения и не определяет
ядро всей экосистемы.

## 6. Бизнес-модель возможностей NEXORA

Внешним компаниям предлагается доступ к конкретным возможностям NEXORA:
например, извлечение структурированных данных из поддерживаемых документов,
проверка происхождения, контекст или диалоговые функции.

До отдельного коммерческого выпуска должны быть подтверждены:
версионируемые контракты, изоляция организаций, аутентификация и отзыв доступа,
лимиты, учёт использования, понятные ошибки, качество поддерживаемых сценариев,
документация и экономическая модель.

Выбор между оплатой за операцию, объём или подписку, точные цены и обещания
доступности остаются отдельными решениями. Эта запись не создаёт тарифы или
платёжные продукты. Текущие услуги PMC и их платёжный выпуск — отдельная работа.

## 7. Удаление ANKH из активной архитектуры

| Область | Новое обозначение | Переход |
|---|---|---|
| Название самостоятельной системы ANKH | NEXORA — разбор документов | Удалить из активной продуктовой и архитектурной иерархии |
| Общий master ANHAM | NEXORA MASTER ARCHITECTURE | Единственный master уровня ядра |
| Продуктовая спецификация ANHAM | ANHAM — AI-система PMC | Сохранить как подчинённый профиль приложения |
| Заголовки AGENTS / CURRENT_STATE / ROADMAP | NEXORA core + PMC application | Обновить и записать принятое решение |
| `docs/ankh/` | Историческая реализация возможностей NEXORA и интеграций PMC | Индекс указывает новую принадлежность; физический перенос выполняется по карте зависимостей |
| `lib/ankh-harness/`, `scripts/ankh/`, `/ankh-test`, `ANKH_HARNESS_ENABLED` | Совместимые технические обозначения до миграции | Переносить с сохранением импортов, флагов и ограничения test-only |
| Google Cloud project/processor, миграции, benchmark artifacts | Стабильные внешние идентификаторы и исторические доказательства | Не переименовывать вслепую; учитывать существующие привязки |
| Символ анкх в графике или объяснении имени ANHAM | Символ центра | Это не имя отдельной AI-системы |

Старые результаты испытаний не переписываются так, будто были получены новым
NEXORA runtime. Продуктовое имя выводится сейчас; полный технический перенос
получает отдельные задачи и доказательства совместимости.

## 8. Последовательность реализации

| ID | Задача | Критерий завершения |
|---|---|---|
| NX-00 | Зафиксировать иерархию, убрать ANKH как отдельную систему, согласовать app profile | Master, AGENTS, CURRENT_STATE, DECISIONS, ROADMAP и план владельца согласованы; рабочая ветка сохранена |
| NX-01 | Составить карту имеющихся функций: общее ядро / предметный код PMC / интерфейс | У каждого компонента есть назначение, текущие потребители и сохраняемые зависимости |
| NX-02 | Выделить контракт «разбор документов» и тонкий адаптер PMC | Существующий тестовый сценарий проходит через контракт без второй копии обработки, источников или Case |
| NX-03 | Продолжить Phase 2.9 и проверить общий контур в изолированной среде | Измерения качества, источники, повторный запуск, права и ручная проверка приняты; без ложного повышения доверия |
| NX-04 | Подключить ANHAM к принятым возможностям через адаптер | Проверенный RU/EN путь клиент → документы → Карен → сохранённый ответ; версия и источник воспроизводимы |
| NX-05 | Подготовить внешний NEXORA API и коммерческую приёмку | Изолированный внешний потребитель использует версионируемую возможность; права, лимиты, учёт и ошибки проверены |
| NX-06 | Расширять каталог возможностей и приложения | Каждый новый сценарий имеет собственные проверенные границы и статус готовности |

Перенос не требует немедленно создавать новый репозиторий, базу или сервер.
Сначала выделяются логические границы в существующей реализации. Физическое
разделение обосновывается нагрузкой, безопасностью и необходимостью независимых выпусков.

## 9. Правила продолжения

Этот файл определяет ядро и принадлежность возможностей.
`CURRENT_STATE.md` описывает фактическую реализацию, `ROADMAP.md` — порядок работ,
`DECISIONS.md` — решения, `AGENTS.md` — правила исполнения.

Прежние запреты production auto-verification, неразрешённой обработки медицинских
данных и автоматической клинической интерпретации сохраняются.
Phase 2.9 остаётся открыта. NEXORA hub, ANHAM interface и коммерческий API имеют
отдельные критерии готовности. Документ не означает их автоматического выпуска.

На следующей задаче читать эти документы и актуальные PR, не восстанавливать
систему только по отдельному чату. Не создавать параллельный master для ANKH
или объявлять аналитическое ядро собственностью ANHAM.
